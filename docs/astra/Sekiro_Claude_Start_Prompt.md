## 1. 기존 작업을 보존하며 변경 반영

먼저 프로젝트 지침, git status와 현재 관련 변경만 확인한다. git reset/clean, 미커밋 작업 삭제, 현재 소스 전체 덮어쓰기는 하지 않는다.

ZIP의 경로 항목을 확인하고 프로젝트 밖의 새 작업 폴더에 푼다. ZIP 내부 README_ko.md, update/base_manifest.json, update/sekiro_feedback.patch 및 해당 코드 차이를 확인한다. 다음을 실제로 읽어 아직 필요한 수정인지 판단한다.

- capture 재시작 시 기존 기록 보존
- 객체/root/child 변경 및 첫 읽기 실패 이후 기준값 폐기
- baseline, 변경 없는 성공 샘플, 실패, gap 기록
- 분석 시 겹치는 시도의 중복 집계 제외
- 입력 worker 종료를 기다린 뒤 파일/프로세스 핸들 해제

update/apply_update.py를 읽고 --repo C:\workspace\sekiro_haptics로 검사만 먼저 실행한다. 변경 대상이 알려진 기준과 일치하고 변경이 필요한 경우 --apply로 적용한다. 현재 코드에 같은 수정이 있으면 중복 적용하지 않는다. 충돌하면 사용자 변경을 보존해 관련 diff를 병합한다. 통과시키려고 해시 목록을 변조하거나 검사 로직을 무력화하지 않는다. 의미가 불명확한 충돌만 구체적으로 질문한다.

출력 구현이 함께 반영되어도 이번 신호 조사의 의존성으로 삼지 않는다. HID 출력은 비활성화해도 된다. 기존 코드에 대응 기능이 이미 있으면 그 구현을 재사용한다.

## 2. Windows 빌드와 필요한 회귀 검증

현재 설치된 빌드 도구와 기존 프로젝트 빌드 방식을 확인한다. 새 빌드 디렉터리에서 probe와 관련 테스트를 빌드하고 이번 변경 때문에 생긴 컴파일 오류를 해결한다. 예시 설정은 다음과 같으며 현재 환경에 맞춰 사용한다.

cmake -S . -B build-deflect -A x64 -DSEKIRO_HAPTICS_BUILD_DUALSENSE_TRANSPORT=OFF
cmake --build build-deflect --config Release --target sekiro_haptics_signal_probe sekiro_haptics_tests capture_v3_fixture

capture_v3 decoder와 deflect_signal 분석 테스트도 실행하라. CTest의 테스트별 이름/명령은 실제 CMake 정의로 확인한다. 합성 fixture 테스트를 게임 인식률로 표현하지 않는다. 실패를 소스 버그, 환경 문제, 미실행으로 나누고 테스트를 삭제하거나 기대값을 약화해 통과시키지 않는다. 테스트 수를 과거의 528/587 같은 숫자에 맞추지 않는다.

## 3. 실제 게임 판정 신호 조사 — 이번 핵심

실행 중인 프로세스 경로, Steam 설치 정보 또는 제한된 설치 경로 확인으로 로컬 sekiro.exe를 찾는다. 찾지 못하면 게임 설치 경로만 요청한다. 실제 파일의 SHA-256, 크기, 적용 모드를 기록하고 현재 사용할 수 있는 정적 분석 도구를 확인한다.

게임 전체 EXE, 대형 메모리 덤프, 모든 함수의 디컴파일을 이 대화나 외부 서비스로 업로드하도록 요구하지 않는다. 로컬 분석 도구로 조사하고 필요한 작은 함수 발췌와 근거만 결과물에 남긴다. 전체 바이너리의 base64/hex 변환도 업로드 대안으로 삼지 않는다. 추가 도구가 없으면 현재 도구로 할 수 있는 작업을 먼저 끝내고 필요한 도구와 이유만 구체적으로 알린다.

우선 일반 방어와 플레이어 튕겨내기가 갈라지는 게임 결과 처리 경로를 좁혀라. 지속되는 결과 기록이 있으면 다음을 확인한다.

- 결과 타입은 무엇으로 구별하는가?
- 방어자가 플레이어임을 어떻게 확인하는가?
- 외부 읽기로 어떤 객체/필드에서 관측할 수 있고 얼마나 유지되는가?
- 같은 동작의 연속 성공을 매번 구별할 실제 발생 식별자나 기록 구조가 있는가?

그런 결과 기록이 확인되지 않으면 플레이어 반응 애니메이션/상태를 조사한다. 일반 방어와 구분되는지, 적도 같은 값을 쓰는지, 같은 ID가 연속 실행될 때 어떻게 구별하는지 확인한다. 함수 이름이나 문자열만으로 성공 판정이라고 결론 내리지 말고 관련 분기·호출자·소유 객체 근거를 남긴다.

HP 무변화, 체간 변화, 가드 입력, parry window만으로 성공 판정을 구현하지 않는다. 기존 GameDataMan/WorldChrMan AOB나 PlayerGameData의 숫자가 읽힌다는 사실도 패링 의미 검증이 아니다. 후보가 없는 영역의 스캔을 무작정 반복하지 않는다.

실제 주소, offset, ID, 카운터가 미확정이면 unknown으로 남긴다. 예제의 합성 ID나 activation을 실제 필드처럼 사용하지 않는다. 관측 샘플 번호·현재 시각으로 게임의 발생 번호를 대신 만들지 않는다. 현재 단계는 게임 파일·메모리를 읽기 전용으로 다룬다. 메모리 쓰기, DLL 주입, 코드 패치, 입력 자동화, 게임/세이브 변경은 수행하지 않는다. 외부 읽기가 충분하지 않다는 근거가 확보된 뒤 관측 hook을 제안할 수 있지만 이번 범위에 임의로 추가하지 않는다.

## 4. 근거 있는 후보만 관측하고 평가

후보 경로가 확보되면 기존 reader/resolver/capture를 재사용해 최소 관측 코드를 구현한다. 플레이어 객체를 읽기 전후 재확인하고 객체 변경·부분 읽기·실패·gap 이후에는 이전 기준값으로 이벤트를 만들지 않는다. static custom-address 캡처는 객체 교체를 자동 추적하지 못하므로 짧은 조사에만 사용한다.

내가 직접 플레이해야 할 시점에 정확한 실행 명령, 기록 파일 위치, 순서대로 할 행동을 알려라. 먼저 플레이어 패링, 일반 방어, 적이 내 공격을 튕김, 허공 방어, 피격, 빠른 연속 패링을 대조한다. 독립 영상과 시계 동기화로 결과를 표시한다. 버튼 marker를 정답으로 자동 전환하지 않는다.

tools/deflect_signal.py가 반영되어 있으면 후보를 고르는 세션과 별도 평가 세션을 분리해 사용한다. 동일 값이 유지되어 연속 성공을 놓친다면 누락으로 보고한다. 결과가 좋은 후보도 player 소유권·게임 의미·수명·연속 발생 구분이 확인되기 전에는 진동 출력에 연결하지 않는다. 우선 raw 관측과 candidate 이벤트를 로그로 확인한다.
