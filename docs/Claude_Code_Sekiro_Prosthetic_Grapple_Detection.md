0. --enemy 모드에서 적 방어·패링의 원인 구분

이번 적 반응 신호의 목표는 플레이어가 실제로 가한 근접 공격을 해당 적이 방어하거나 패링했을 때 발생하는 피드백이다. 플레이어 자신이 적 공격을 방어·패링하는 이벤트와 방향을 혼동하지 마라.

반드시 구분할 조건:
- 플레이어의 기존 칼 근접 공격 → 실제 피격 대상 적이 방어/패링: 기존 정상 검출을 유지한다.
- 적 A의 공격 → 적 B가 방어/패링: 이 적 반응 피드백은 발생하지 않는다.
- 플레이어의 표창 → 적이 방어/패링: 이 적 반응 피드백은 발생하지 않는다.
- 표창을 선택만 해 둔 상태에서 플레이어가 칼로 공격 → 적이 방어/패링: 정상 검출되어야 한다.

관측할 적 객체를 고르는 것과, 그 반응의 원인이 플레이어 공격인지 확인하는 것은 별개다. 현재 락온, 가까운 적, 이전에 내가 때린 적, 최근 R1 입력만으로 원인을 확정하지 마라. 내가 때린 적이 이후 다른 적의 공격을 막는 경우도 제외되어야 한다. 실제 충돌 상대를 기준으로 하며, 락온 여부만으로 허용 대상을 제한하지 마라.

현재 코드가 무엇을 근거로 적 반응을 발생시키는지 추적해라. 관측 가능한 충돌/공격 결과 기록에서 공격자, 방어자, 공격 종류, 해당 반응과 연결되는 식별자·순번 등의 근거를 조사해라. 이 항목들은 필요한 의미를 설명한 것이며 게임에 같은 이름의 필드가 있다는 뜻은 아니다.

투사체 소유자가 플레이어여도 표창 반응은 제외해야 하므로 공격자 확인만으로 충분하지 않다. 현재 선택 의수만 보고 판정하지 말고, 해당 반응을 유발한 실제 공격을 분류해라. 다른 의수 전체를 이번 표창 제외 규칙으로 일괄 차단하지 마라. 사비마루 등 추가 의수의 별도 사용 이벤트는 후속 단계의 범위로 유지하고, 적 반응과의 연결 정책을 임의로 확장하지 마라.

마지막 공격자/피격 기록이 남아 있는 구조라면 오래된 값이 현재 반응에 붙지 않도록 신선도와 같은 충돌에 속한다는 근거를 확인해라. 적 객체 교체·재탐색·주소 재사용·읽기 실패·로드 이후에는 과거 원인과 새 반응을 결합하지 마라.

표창 입력 후 일정 시간 모든 신호를 막거나, 의수 선택 중 항상 막거나, cooldown으로 해결하지 마라. 표창 직후 정상 칼 공격과 적끼리의 교전이 겹쳐도 각각 구분해야 한다. 필요한 원인 정보가 확인되지 않으면 미확정 반응으로 로그에 남기고, 확정된 플레이어 근접 반응으로 출력하지 마라. 모든 신호를 꺼 오검출만 0이 된 것을 해결로 보고하지 마라.

raw 적 반응과 채택된 이벤트를 분리하고, 관측 근거가 있는 범위에서 객체 식별, 공격 주체/종류, 채택 또는 제외 이유, 시각을 남겨라. 알 수 없는 정보는 unknown으로 기록해라. 실제 신호가 부족해 상관관계만 확보된 경우 그 한계와 다음 관측을 보고하고, 인과관계 검증이 끝났다고 쓰지 마라.

최소 검증 장면은 플레이어 칼 공격의 적 방어/패링, 적끼리만의 전투, 내가 전에 공격한 적의 이후 NPC 교전, 표창 방어/패링, 표창 선택 상태의 칼 공격, 표창 직후 칼 공격, 연속 근접 공격, 타깃 전환과 로드다. 정상 검출의 누락과 오검출을 함께 보고하고 원시 로그를 보관해라.

표창 사용/발사 자체는 추후 별도의 의수 이벤트로 감지할 수 있다. 이번 요구는 표창 때문에 적 방어·패링용 피드백이 잘못 발생하는 것을 막는 것이다. 원시 관측 자료를 지우거나 표창 조사 기능 자체를 없애지 마라.

1. 기존 기반과 작업 범위

AGENTS.md와 관련 코드를 읽고 기존 ProcessReader, 주소 해석, capture/replay, detector, OutputRuntime을 재사용해라. 트리거와 PCM Mixer를 다시 만들지 마라. 기존 패링·일반 방어의 정상 검출과 소리 겹침 동작을 보존하면서, 위에 명시한 --enemy 오검출 판정을 수정해라.

이번에는 새 게임 신호 탐색과 감지 확장이 작업 범위다. 이전 출력 런타임 개발 지시에서 새 신호 탐색을 제외했던 것은 그때의 범위였으며, 이번 작업에서는 의수와 와이어 신호를 조사한다. 날카로운 접촉감, 금속성 음색, 진동 강도·주파수 튜닝, GUI는 이후 과제로 유지한다.

게임 접근은 기존 읽기 전용 방식을 유지한다. 실제 EXE 지문과 포인터 유효성 검사를 유지하고, 모르는 offset·장비 ID·애니메이션 ID를 임의로 채우지 마라. 기존 패링 신호가 의수나 와이어 동작도 알려준다고 가정하지 마라.

2. 현재 선택한 의수부터 식별

장착 슬롯에 들어 있는 의수 목록과 지금 사용할 수 있도록 선택된 의수를 구분해라. 표창과 사비마루 사이를 전환할 때 선택 상태가 바뀌고, 사용하지 않고 전환만 해도 그 차이를 관측할 수 있어야 한다.

원시 ID와 의미를 연결한 근거를 기록해라. 강화형은 실제 관측한 것만 같은 계열로 묶고, 확인하지 않은 ID는 unknown으로 남겨라. 메뉴·로드·사망·객체 교체·읽기 실패 이후 이전 선택 상태를 계속 유효한 것으로 취급하지 마라.

먼저 출력 없이 현재 선택 상태와 변화 시각을 로그로 확인할 수 있게 해라. 같은 상태를 매 polling마다 새 이벤트처럼 발생시키지 마라.

3. R2 입력과 실제 의수 사용을 구분

표창을 선택한 상태에서 R2를 눌렀는지, 사비마루를 선택한 상태에서 R2를 눌렀는지는 사용 시도 정보다. 게임이 실제로 해당 동작을 시작했는지까지 별도로 확인해라.

입력은 현재 입력 경로에서 읽을 수 있으면 보조 정보로 기록하고, 플레이어의 행동 상태·애니메이션 전환·관측 가능한 실행 기록 등에서 실제 동작 근거를 조사해라. 버튼 입력만으로 성공적인 사용을 확정하지 마라. 스킬 시작, 표창 발사, 적 명중도 각각 다른 의미로 취급해라.

가능한 신호가 애니메이션 시작뿐이면 사용 시작까지만 검증했다고 보고해라. 실제 발사나 명중까지 알아낸 것처럼 명명하지 마라. 이 단계에 필요한 이벤트 이름은 새로 정의하는 내부 모델이며, 게임에 같은 이름의 필드가 존재한다는 뜻이 아니다.

사비마루는 우선 연속 동작의 시작과 종료를 목표로 해라. 개별 베기를 구분할 근거가 확보됐을 때만 각 타격 이벤트로 확장하고, R2 한 번이나 고정 타이머로 베기 횟수를 만들어내지 마라.

연속 사용과 같은 애니메이션 재실행을 구별할 방법을 확인해라. 고정 cooldown으로 새 사용을 버리지 마라. 동작 도중 의수를 바꿀 수 있는 상황에서는 시작 당시 의수를 해당 동작에 연결하고, 처리 시점의 선택 상태로 소급 변경하지 마라.

4. 와이어 액션 감지

와이어 입력, 와이어를 사용할 수 있는 대상의 존재, 실제 와이어 동작은 구분해라.

첫 목표는 실제 와이어 동작 시작과 종료/취소를 구별하는 것이다. 발사·걸림·당겨지는 이동·도착까지 단계별로 구분할 근거가 확보되면 추가해라. 확보되지 않은 단계는 임의의 시간표로 추정해 실제 게임 이벤트처럼 내보내지 마라.

일반 점프·낙하·벽 동작·대상이 없는 상태의 입력과 혼동하지 않는지 확인해라. 관측이 끊겼을 때는 동작이 정상 완료된 것으로 처리하지 말고 unknown/cancelled 등 적절한 관측 종료 사유로 정리해라.

5. 실제 관측과 검증

기존 CLI에 필요한 최소 관찰 기능을 추가하고, 게임 프로세스가 있으면 실제 빌드를 확인한 뒤 관측을 시작해라. 게임이 없으면 가능한 코드 조사와 준비를 마친 다음 필요한 실행·플레이 절차를 안내해라.

내가 수행할 장면을 짧게 나눠 안내해라.
- 의수 교체만 하기, 표창 사용, 사비마루 사용 및 연속 동작.
- 사용할 수 없는 상태에서 입력, 일반 공격·패링·메뉴 조작.
- 실제 와이어 이동, 대상 없는 입력, 일반 점프와 낙하.

각 장면에서 읽은 원시 값, 선택 의수, 동작 상태, 발생 이벤트와 시각을 함께 남겨라. 성공과 실패의 정답은 영상 또는 실제 플레이 확인을 근거로 기록하고, 버튼이나 수동 marker 시각을 게임 동작 시각과 동일시하지 마라.

후보 규칙을 정한 뒤 다른 플레이 세션에서도 확인해라. 반복 사용 누락, 잘못된 의수 분류, 비슷한 다른 행동의 오검출, 로드 후 가짜 이벤트를 확인해라. 실제 자료와 합성 fixture를 구분하고, 확인된 것만 자동 출력에 연결해라. 기존 패링/방어도 짧게 회귀 검증해라.

6. 검증된 신호를 기존 Trigger/PCM에 연결

현재 선택한 의수 같은 지속 상태와 실제 사용 시작 같은 순간 이벤트를 구분해 기존 구조에 최소한으로 추가해라. Detector에서 HID/WASAPI를 직접 호출하지 마라.

R2를 누르는 동안 의수별 저항을 느끼게 하려면, 선택 상태와 플레이 가능한 상태를 바탕으로 누르기 전에 준비 저항을 설정해야 한다. 실제 발동을 감지한 뒤에만 저항을 켜는 구조로 만들지 마라. 표창/사비마루별 준비 저항과 실제 사용 때의 PCM 피드백을 구분하고, 우선 이미 확인된 단순 효과를 사용해라.

와이어도 현재 버튼 매핑을 확인해 연결해라. 버튼을 놓은 뒤에는 트리거 저항을 손가락으로 느끼기 어려울 수 있다는 점을 실제 체감 확인 항목에 포함해라. 버튼 유지나 재매핑을 강요하지 마라.

메뉴·로드·사망·상태 불명·연결 해제에서는 준비 저항을 해제하고, 실제 동작의 종료·취소에서도 효과 수명을 정리해라. 관측이 끊겨도 저항이 무기한 남지 않게 해라. 상태 기반 준비 효과와 순간 효과가 같은 트리거를 사용할 때 교체·복귀 규칙을 정하고, 오래된 효과의 만료가 현재 효과를 끄지 않게 해라.

보고할 때는 실제 관측으로 확인한 신호와 근거, 구현한 감지 범위, 실행한 테스트, 아직 후보인 부분, 내가 체감 확인할 명령을 구분해라. 실제 신호를 찾지 못했다면 그 사실과 다음에 필요한 관측을 명확히 제시해라. 기능 이름과 합성 테스트만 추가하고 게임 감지가 완료됐다고 보고하지 마라.
